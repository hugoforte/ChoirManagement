# Auth Provider Comparison: Convex Auth vs. Clerk vs. Auth0

Purpose: compare Convex Auth, Clerk, and Auth0 as the login/role layer for ChoirManagement — a self-hosted, one-deployment-per-choir Vite+React/Convex app operated by a non-professional volunteer — to inform (not yet make) a decision on Google OAuth + username/password login and Admin/Director/Member roles.

All findings below are sourced live (Sept 2026); each non-obvious claim is inline-cited with URL and access date. This is **research input, not an ADR** — an ADR should be recorded in `docs/adr/` once the maintainer decides, per `docs/agents/domain.md`.

---

## 1. Convex Auth (`@convex-dev/auth`): maturity and capabilities

- **Status: beta / early preview, not presented as production-hardened.** The main auth overview page states Convex Auth is "in beta" ([docs.convex.dev/auth](https://docs.convex.dev/auth), accessed 2026-09-10), and the project's own FAQ says "Convex Auth is early preview" ([labs.convex.dev/auth/faq](https://labs.convex.dev/auth/faq), accessed 2026-09-10). Convex's docs explicitly flag it as incomplete: "Convex Auth is in beta (it isn't complete and may change in backward-incompatible ways) and doesn't provide as many features as third party auth integrations" ([docs.convex.dev/auth](https://docs.convex.dev/auth), accessed 2026-09-10).
- **Password provider: yes, out of the box.** `@convex-dev/auth/providers/Password` is a first-class provider; wiring it in is a few lines in `convex/auth.ts` ([labs.convex.dev/auth/config/passwords](https://labs.convex.dev/auth/config/passwords), accessed 2026-09-10).
- **Google OAuth: yes, out of the box** via `@auth/core/providers/google`, configured the same way ([labs.convex.dev/auth/config/oauth/google](https://labs.convex.dev/auth/config/oauth/google), accessed 2026-09-10). Support for "GitHub / Google / Apple etc." OAuth plus magic links/OTP and passwords is listed on the overview page ([docs.convex.dev/auth/convex-auth](https://docs.convex.dev/auth/convex-auth), accessed 2026-09-10).
- **Known limitations / rough edges relevant to a small production app:**
  - No built-in UI components — you copy sign-in form code from the docs/example repo and own it yourself ([docs.convex.dev/auth/convex-auth](https://docs.convex.dev/auth/convex-auth), accessed 2026-09-10).
  - Framework scope is narrower than the third-party options: officially it "currently supports client-side React web apps served from a CDN and React Native mobile apps" (a good fit for this project's Vite+React SPA, but worth noting as a stated boundary) ([docs.convex.dev/auth/convex-auth](https://docs.convex.dev/auth/convex-auth), accessed 2026-09-10).
  - Email verification is **optional**, not automatic — you must wire a `verify` step (e.g. via Resend + an OTP flow) if you want it; unverified accounts work by default ([labs.convex.dev/auth/config/passwords](https://labs.convex.dev/auth/config/passwords), accessed 2026-09-10).
  - Self-hosted-backend caveat (only relevant if a choir ever ran the open-source `convex-backend` Docker option, which this project's confirmed architecture explicitly avoids): the Convex Auth CLI initializer "does not support self-hosted deployments yet," requiring manual setup instead (found via web search of Convex Auth OAuth docs, accessed 2026-09-10). Since every choir here runs its own **Convex Cloud** project, not the self-hosted Docker backend, this caveat does not currently apply — but it's a signal the library's tooling assumes the hosted-cloud path.
  - No independent confirmation was found of a 1.0/GA release; all primary sources continue to use "beta"/"early preview" language as of the access date above.

## 2. Convex + Clerk

- **Mechanism:** Clerk issues session JWTs; Convex validates them by trusting Clerk's issuer domain. You create a `convex/auth.config.ts` with a `providers` entry whose `domain` is your Clerk "Frontend API URL" (e.g. `https://verb-noun-00.clerk.accounts.dev` in dev) and `applicationID: "convex"` (matching the `aud` claim on a Convex-specific JWT template in Clerk) ([docs.convex.dev/auth/clerk](https://docs.convex.dev/auth/clerk), accessed 2026-09-10).
- **Cost at small scale (20-100 members):** Clerk's free plan, per its own pricing page, allows **"50,000 MRU (monthly retained user) limit per app"** — MRU (monthly *retained* users) is a narrower unit than MAU used by other vendors — plus unlimited applications, custom domain, and prebuilt sign-in/sign-up/profile UI, but **excludes MFA, passkeys, enterprise connections (SAML/OIDC), and user bans** ([clerk.com/pricing](https://clerk.com/pricing), accessed 2026-09-10). A 20-100 member choir is trivially inside the free MRU cap; the excluded features (MFA, SAML) are not required for this project's stated scope (Google OAuth + password + basic roles). The next paid tier, Pro, is **$25/mo ($20/mo billed annually)** and adds MFA, passkeys, branding removal, and enterprise connections ([clerk.com/pricing](https://clerk.com/pricing), accessed 2026-09-10) — not needed here.
- **Per-choir account model:** Clerk's docs describe the integration as one Clerk **application** per app instance (create an application, activate the Convex integration on it, copy its Frontend API URL) ([docs.convex.dev/auth/clerk](https://docs.convex.dev/auth/clerk), accessed 2026-09-10). A single shared Clerk app across many choirs is technically possible (Clerk supports multi-tenant "Organizations" so one user pool can be partitioned into isolated tenants with per-tenant roles) ([clerk.com/docs/guides/organizations/overview](https://clerk.com/docs/guides/organizations/overview), accessed 2026-09-10), **but it would break this project's per-choir Convex Cloud deployment model**: every choir's Convex backend would trust the *same* Clerk issuer/JWT, so without extra application-level checks a valid token minted for Choir A's Clerk "Organization" could authenticate against Choir B's independent Convex deployment too, since `auth.config.ts` only checks issuer + audience, not org membership, unless the developer adds that check. It would also concentrate all choirs' auth on one third party account owned by the OSS maintainer, undermining the self-hosting-independence goal (single point of failure/billing/governance, and one app's MRU usage counts against the shared 50k cap). The straightforward, isolation-preserving pattern is **one Clerk account + one Clerk application per choir**, matching the one-Convex-deployment-per-choir model.

## 3. Convex + Auth0

- **Mechanism:** same OIDC/JWT pattern — Convex "is compatible with most authentication providers because it uses OpenID Connect (based on OAuth) ID tokens in the form of JWTs to authenticate" requests, and `auth.config.ts` is pointed at the Auth0 tenant domain/audience ([docs.convex.dev/auth/auth0](https://docs.convex.dev/auth/auth0), accessed 2026-09-10). Frontend wiring wraps the app in `Auth0Provider` (from `@auth0/auth0-react`) nested inside `ConvexProviderWithAuth0` ([docs.convex.dev/auth/auth0](https://docs.convex.dev/auth/auth0), accessed 2026-09-10).
- **Cost at small scale:** Auth0's free plan supports **"Up to 25,000 monthly active users,"** with no credit card required, and notably does **not** gate social connections or MFA on the free tier ("Unlimited Social Connections," "Pro Multi-Factor Authentication" included, 1 custom domain) — but organizations are capped at 5 and only 1 enterprise connection is included ([auth0.com/pricing](https://auth0.com/pricing), accessed 2026-09-10). A 20-100 member choir is well within the free MAU cap. Essentials, the next tier, starts "from $35/month" at a much higher (500+) MAU tier and adds separate prod/dev environments and standard support ([auth0.com/pricing](https://auth0.com/pricing), accessed 2026-09-10) — not needed at this scale.
- **Per-choir signup burden:** Auth0's setup docs are written around creating your own tenant/application ("Sign up for free at Auth0," configure callback/logout/allowed-origin URLs on that application) ([docs.convex.dev/auth/auth0](https://docs.convex.dev/auth/auth0), accessed 2026-09-10). As with Clerk, sharing one Auth0 tenant across many independently-deployed choir Convex backends would mean every choir's backend trusts the same issuer and the app would need to build its own tenant-isolation logic on top (Auth0's free-tier "Organizations" cap of 5 would also become a hard ceiling on how many choirs could even be represented). The natural, isolation-preserving pattern is again **one Auth0 account + tenant per choir**.

## 4. Setup complexity comparison (Google login + password login, frontend + Convex backend)

| Step type | Convex Auth | Clerk | Auth0 |
|---|---|---|---|
| Third-party accounts to create | 0 extra services beyond a Google Cloud project (which you'd need for Google OAuth regardless of provider) | 1 (Clerk account) | 1 (Auth0 account) |
| Google Cloud Console work | Create/select project, configure OAuth consent screen, create a Web OAuth client with the Convex HTTP Actions URL as redirect URI ([labs.convex.dev/auth/config/oauth/google](https://labs.convex.dev/auth/config/oauth/google), accessed 2026-09-10) | Same Google Cloud Console OAuth client creation, but configured *inside* Clerk's dashboard as a "social connection" rather than wired directly into your own backend code | Same Google Cloud Console OAuth client work, configured as a Social Connection inside the Auth0 dashboard |
| Provider-side app/tenant setup | None (no separate provider) | Create a Clerk application; enable password + Google social connection; activate the Convex integration in Clerk's dashboard ([docs.convex.dev/auth/clerk](https://docs.convex.dev/auth/clerk), accessed 2026-09-10) | Create an Auth0 tenant/application; configure callback/logout/origin URLs; enable a database (password) connection and the Google social connection ([docs.convex.dev/auth/auth0](https://docs.convex.dev/auth/auth0), accessed 2026-09-10) |
| Convex backend config | `npx @convex-dev/auth` CLI scaffolds `convex/auth.config.ts`, edits `convex/schema.ts` (add `authTables`); add `Password` + `Google` providers in `convex/auth.ts`; set 2 env vars via `npx convex env set AUTH_GOOGLE_ID/…SECRET` ([labs.convex.dev/auth/setup](https://labs.convex.dev/auth/setup), [labs.convex.dev/auth/config/oauth/google](https://labs.convex.dev/auth/config/oauth/google), accessed 2026-09-10) | Hand-write `convex/auth.config.ts` with `domain`/`applicationID`; set 1 env var (`CLERK_JWT_ISSUER_DOMAIN`) on the Convex dashboard/CLI ([docs.convex.dev/auth/clerk](https://docs.convex.dev/auth/clerk), accessed 2026-09-10) | Hand-write `convex/auth.config.ts` with domain/applicationID; set `AUTH0_DOMAIN`/`AUTH0_CLIENT_ID` env vars on the Convex dashboard ([docs.convex.dev/auth/auth0](https://docs.convex.dev/auth/auth0), accessed 2026-09-10) |
| Frontend config | Swap `ConvexProvider` for `ConvexAuthProvider`; build your own sign-in form (copy from example repo) | Install `@clerk/react`; set 1 env var (publishable key); wrap app in `ClerkProvider` → `ConvexProviderWithClerk`; use Clerk's prebuilt `<SignInButton>`/`<UserButton>` UI | Install `@auth0/auth0-react`; set 2 env vars (domain, client ID); wrap app in `Auth0Provider` → `ConvexProviderWithAuth0`; build your own login button via `useAuth0()` |
| Rough total distinct steps to get both Google + password working | ~7-8 (CLI init, schema edit, provider file edits ×2, 2 env vars, Google Cloud client, build your own UI) | ~9-11 (Clerk signup, app creation, enable connections, activate Convex integration, copy issuer URL, 1 backend env var, frontend package + 1 env var + provider wiring, Google Cloud client) — more *accounts/clicks* up front but least code, prebuilt UI | ~10-12 (Auth0 signup, tenant/app creation, configure URLs, enable connections, 2 backend env vars, frontend package + 2 env vars + provider wiring, Google Cloud client, build your own UI) — most manual dashboard configuration |

Net: Convex Auth has the fewest external accounts (good for self-hosting independence — no third-party dependency at all) but pushes more code-ownership (UI, verification flow) onto the volunteer. Clerk has the most "batteries included" (prebuilt UI, one issuer URL to copy) at the cost of one more account dependency. Auth0 sits in between/slightly more manual than Clerk for the same dependency cost, with less generous free-tier polish (no prebuilt UI referenced in the Convex integration docs).

## 5. Official Convex guidance on Convex Auth vs. third-party providers

Convex's own docs do give explicit comparative guidance, though **none of it specifically addresses self-hosted/open-source/community projects vs. VC-funded SaaS startups** — that framing does not appear anywhere in the primary sources checked.

- `docs.convex.dev/auth` frames Convex Auth as: "the quickest way to get auth up and running" because it "doesn't require signing up for another service," while explicitly caveating it is "in beta (it isn't complete and may change in backward-incompatible ways) and doesn't provide as many features as third party auth integrations" (accessed 2026-09-10).
- The same page frames third-party providers (Clerk, Auth0, etc.) as offering "the most comprehensive authentication solutions" with "a ton of functionality like passkeys, two-factor auth, spam protection," and recommends Clerk or Auth0 specifically "for advanced authentication functionality like SSO and MFA" (accessed 2026-09-10, via search-indexed content of docs.convex.dev/auth).
- No page on docs.convex.dev or convex.dev/blog was found that ties this choice to deployment topology (self-hosted vs. managed SaaS) or to project governance model (OSS community project vs. funded startup). The closest thing to relevant guidance is purely about *feature completeness and stability* (beta vs. mature) and about *not wanting to add a third-party dependency* — which happens to align with, but is not framed around, self-hosting independence.

## Recommendation

**Recommend Clerk** for this project, as a considered departure from the maintainer's initial lean toward Convex Auth, with the following reasoning:

1. **Convex Auth's own docs disqualify it for a "ship once, hand to a non-professional volunteer, don't touch it again" deployment.** Both primary sources describing its status ("beta," "early preview," "may change in backward-incompatible ways") are Convex's own words, not third-party skepticism. A volunteer operator with no engineering team behind them is exactly the profile least equipped to absorb a breaking change in the auth library, debug a half-built email-verification flow, or hand-maintain a custom sign-in UI. This risk outweighs the self-hosting-independence benefit for this specific user profile.
2. **Cost is a non-factor.** Both Clerk (50,000 MRU free) and Auth0 (25,000 MAU free) comfortably cover a 20-100 member choir with zero cost, even under worst-case pricing-model changes cited in secondary sources.
3. **Clerk beats Auth0 on volunteer-operability specifically**, which is the deciding axis given the stated persona: Clerk provides prebuilt sign-in/sign-up UI components (Auth0's Convex integration docs assume you build your own), a single issuer-URL copy-paste plus one Convex env var, and a dedicated, documented Convex integration surface (`docs.convex.dev/auth/clerk`, plus a Clerk-side "Convex integration" activation button) that is more turnkey than Auth0's more manual, enterprise-oriented dashboard.
4. **Self-hosting independence is preserved at the deployment level, not the vendor level, in either case.** Since the architecture is already one Convex Cloud project per choir, per-choir isolation is achieved by each choir creating its **own** Clerk application (not a shared one) — this keeps the "one deployment = one choir" property intact and avoids the cross-tenant JWT-trust problem described in section 2, while still depending on a well-documented external service rather than a beta library.

This is a recommendation for the maintainer's consideration, not a decision. If/when the maintainer decides, record it as an ADR in `docs/adr/` per this repo's convention (`docs/agents/domain.md`), since this document is research input only.
