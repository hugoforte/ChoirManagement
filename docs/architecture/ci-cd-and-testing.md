# CI/CD & testing strategy

Resolved wayfinder ticket [#5](https://github.com/hugoforte/ChoirManagement/issues/5) — merged to `main`, and the deploy pipeline has been run for real against a live Vercel project + Convex production deployment (not just designed on paper). The exact test *surface* (which functions, which components) is intentionally left vague — that follows from the schema ticket (#2), long since resolved, but E2E coverage of it is still growing.

Revised after reviewing [hugoforte/hugo-tessa-20-years](https://github.com/hugoforte/hugo-tessa-20-years), a prior Convex project with a proven CI/CD + E2E setup worth adopting directly rather than reinventing.

## Deploy: no GitHub Actions deploy step

Vercel is the recommended frontend host (for both the maintainer's demo and, per the setup guide, self-hosters). Convex's own [Vercel integration](https://docs.convex.dev/production/hosting/vercel) means **deploy isn't a GitHub Actions job at all**: set Vercel's Build Command to `npx convex deploy --cmd 'npm run build'` with a `CONVEX_DEPLOY_KEY` env var (Production-scoped for `main`, **preview-type** for branches — so each branch provisions its own isolated Convex backend, auto-seeded by `--preview-run seed:preview`). Push to the connected branch → Vercel builds and deploys the frontend, and `convex deploy` deploys the functions, together, natively. This removes the `deploy-prod.yml` / `deploy-demo.yml` workflows from the earlier draft entirely.

**Settled 2026-09-11 — Clerk *does* work on ephemeral preview URLs.** This doc previously claimed the opposite. Verified empirically against a real branch preview (`choir-management-git-chore-branch-p-421061-…vercel.app`): Clerk initialised (its dev-key console notice appeared), and `/` correctly resolved `isSignedIn: false` and redirected to `/public/events` — the exact code path that previously hung forever. Clerk's *development* keys (what this project uses) are designed for arbitrary origins, carrying session state in a `__clerk_db_jwt` querystring parameter instead of an origin-bound cookie; Clerk *production* keys would never work there.

The original "Clerk can't do previews" conclusion was a misdiagnosis: preview builds had no `VITE_CLERK_PUBLISHABLE_KEY` at all (it was scoped to Production only), and the preview build was failing outright for a missing `CONVEX_DEPLOY_KEY`, so Clerk never had a chance to load. **Consequence**: authenticated E2E (`chromium-director`) now runs against the PR's own branch preview rather than only post-merge against production.

## Workflows

1. **`pr-checks.yml`** — every PR (any base branch, not just `main`) and every push to `main`: `npm run check` (typecheck `convex/`, typecheck the app, `vite build`) then `npm test` (Vitest + `convex-test`). Required status check before merge. **Confirmed green against real code.** The `pull_request` trigger deliberately carries no `branches:` filter — a PR based on another PR's branch (a stacked PR, via `gh stack`) still needs this job to run and report, or the required "check" status sits as "Expected" forever and blocks the stack from merging (found when adopting `gh stack`, see #45).
2. **`preview-playwright.yml`** — Playwright E2E in three jobs. On a PR the two preview jobs target that branch's own auto-seeded deployment; production gets a separate read-only smoke suite.
   - **`e2e-guest`**: PRs only (skips drafts and forks). Resolves the branch's Vercel preview and runs the deterministic, Clerk-free `chromium-guest` project. Its public Event detail assertions intentionally rely on `seed:preview` fixtures and therefore never run against production.
   - **`e2e-authenticated`**: **PRs only**, resolving that branch's own *preview* URL (production deliberately holds no test Member rows — the accounts have trivial passwords and production is publicly reachable). Runs `chromium-director` and `chromium-admin` — both **real**, backed by `+clerk_test@example.com` Clerk accounts and Member rows seeded at those Roles (`convex/seed.ts`'s `upsertRoleMember`, driven by `scripts/e2e/seed-role-members.mjs`) — no by-hand promotion step. Sign-in goes through `@clerk/testing`'s email-based ticket strategy (`clerk.signIn({ page, emailAddress })` in `e2e/auth.setup.ts`) — it looks the user up via the Clerk Backend API and mints a sign-in token, no UI form automation, no password, no OTP email. `chromium-chorister` is still absent (no chorister-only UI exists yet to assert against). There is no reseed step in this workflow at all: each branch's preview backend seeds itself via `--preview-run seed:preview` when Convex provisions it.
   - **`production-smoke`**: pushes to `main` and a daily schedule. On pushes it first waits for the matching Vercel production deployment to become ready, then runs `chromium-production-smoke` against the stable production alias. The suite is Clerk-free, read-only, and independent of seed data. `PRODUCTION_BASE_URL` can override the repository default, and optional `PRODUCTION_PUBLIC_EVENT_ID` enables a detail-page canary for a real public Event.
   - The two preview jobs check for `VERCEL_TOKEN` / `VERCEL_PROJECT_ID` / `VERCEL_TEAM_ID` first and **skip with a notice, not a failure**, if absent — a self-hoster's fork without Vercel wired up doesn't get red CI for it. Production smoke needs those credentials only to wait for a just-pushed deployment; its scheduled run checks the stable URL directly. **These three secrets are set** on `hugoforte/ChoirManagement` as of this writing.
   - All three jobs upload `playwright-report/` and `test-results/` as a build artifact (`if: failure()`, 7-day retention) — before this, a failed run's trace/screenshot only ever existed on the CI runner's now-discarded disk (see #34).

## Testing

- **Vitest** for unit tests and React component tests (Testing Library) — one config, two environments via `environmentMatchGlobs`: `convex/**/*.test.ts` under `edge-runtime`, `src/**/*.test.{ts,tsx}` under `jsdom` (see #34). The jsdom project mocks `@clerk/clerk-react` and `convex/react` at the module boundary — no real Clerk session, Convex client, or Vercel preview needed to test the gate's own state machine or a mutation's failure path, unlike everything below this line.
- **`convex-test`**, using `t.withIdentity()` (per the earlier auth research, [`docs/research/convex-clerk-integration-pattern.md`](../research/convex-clerk-integration-pattern.md)) to unit-test Role-based authorization without a real Clerk account or a full E2E run.
- **Playwright**, run in CI against real deployed URLs — `playwright.config.ts` reads `PLAYWRIGHT_BASE_URL` (default `localhost:5173` for local runs). PR suites use the resolved immutable preview deployment; production smoke uses the stable alias so DNS, redirects, SPA routing, the frontend bundle, and the public Convex query are covered together.
- **Role-scoped Playwright projects**: `chromium-director` is real (`e2e/library-manage.spec.ts` exercises the director-only Music Library management flow, #11, and `e2e/events-manage.spec.ts` the Event create/RSVP flow, #13), backed by a `setup` project (`e2e/auth.setup.ts`) that signs in once and saves `storageState` to `.auth/director.json`. `chromium-admin` is real too (`e2e/settings-manage.spec.ts` for the admin-only Settings flow, #14, and `e2e/members-manage.spec.ts` for Role management, #12), signed in as `admin+clerk_test@example.com` and saved to `.auth/admin.json`. `chromium-chorister` isn't built — no chorister-only UI exists yet to assert against.

## Merge gate

`main` is GitHub branch-protected: a PR is required to merge (0 approvals needed — solo project), and it can only merge once the `check` and `e2e-guest` status checks pass (when Vercel secrets are configured — see skip behavior above). This is enforced, not just convention — direct pushes to `main` are rejected by GitHub itself. `e2e-authenticated` runs on the PR but is **not** a required check — so a flake in it can't wedge a merge, while still surfacing authenticated breakage before merge rather than after.

Each feature branch deploys to its own Vercel preview URL **and its own isolated Convex backend**, provisioned automatically by a preview-type deploy key and named after the branch (e.g. `preview/chore-branch-pr-workflow`). Convex auto-runs `seed:preview` on each new one, which seeds demo content plus one Member per Role — so a reviewer can sign in as `admin+clerk_test@example.com` (password `a`) and already hold that Role, with nothing to run by hand. Preview backends auto-delete after 5 days and count against a 40-deployment free-plan cap; `.github/workflows/cleanup-preview.yml` deletes both the Convex preview backend and every Vercel preview deployment for a branch the moment its PR closes (merged or not), rather than waiting on that grace period — Vercel has no equivalent cap or auto-expiry of its own. Production is untouched until merge, so a PR's preview URL is where a feature gets verified — not production. Mechanics and caveats: [`../guides/setup-automation-notes.md`](../guides/setup-automation-notes.md).
